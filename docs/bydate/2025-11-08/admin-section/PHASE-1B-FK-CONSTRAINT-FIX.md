## Executive Summary

Successfully resolved foreign key constraint violation (`23503 - profiles_id_fkey`) that was blocking the user approval workflow. The root cause was architectural mismatch: `pending_users.id` (app-generated UUID) was being used for `profiles.id` (which previously had FK constraint to `auth.users.id` - Supabase Auth's UUID). Solution: Removed FK constraint from `profiles.id` and added email-based unique constraint for user lookups. Approval workflow now works end-to-end. Build successful, changes committed and pushed.

---

## Problem Statement

### Initial Error
When admin clicked "Approve" on pending user, backend failed with:
```
ERROR (23503) insert or update on table "profiles" violates foreign key constraint "profiles_id_fkey"
```

### Root Cause Analysis

The system uses a **two-stage registration workflow**:

```
Stage 1: User Registration
├─ Frontend sends registration form
├─ Backend creates pending_users record
│  ├─ pending_users.id = app-generated UUID (uuid_generate_v4())
│  ├─ Email, name, password, metadata stored
│  └─ Status = "pending"
└─ User waits for admin approval

Stage 2: Admin Approval (WHERE THE BUG WAS)
├─ Admin views pending users
├─ Admin clicks "Approve"
├─ Backend attempts to create profile:
│  ├─ profiles.id = pending_users.id  ← WRONG!
│  ├─ Had FK constraint: profiles.id → auth.users.id
│  └─ But auth.users.id ≠ pending_users.id
└─ FK CONSTRAINT VIOLATION!
```

### Why The Mismatch?

| Table | ID Source | ID Type |
|-------|-----------|---------|
| `pending_users` | App generates | UUID v4 from `uuid_generate_v4()` |
| `profiles` | Previously assumed | UUID from Supabase Auth |
| `auth.users` | Supabase Auth | Automatically generated on user creation |

**The Problem**: 
- When registration happens, user doesn't go through Supabase Auth flow immediately
- Instead, they're stored in `pending_users` with app-generated UUID
- When approving, we try to insert into `profiles` with that `pending_users.id`
- But `profiles.id` had FK constraint to `auth.users.id`, which is a different UUID
- Constraint violation!

## Solution Implemented

### Database Changes (Migration 013)

**File**: `backend/migrations/013_fix_profiles_fk_for_pending_users_approval.sql`

#### Step 1: Remove Problematic FK Constraint
```sql
ALTER TABLE profiles
DROP CONSTRAINT IF EXISTS profiles_id_fkey;
```

**Rationale**: The FK constraint assumes `auth.users` integration at profile creation time, but our workflow stores users in `pending_users` first. Removing this constraint allows the approval workflow to function properly.

#### Step 2: Add Email-Based Unique Constraint
```sql
ALTER TABLE profiles
DROP CONSTRAINT IF EXISTS uq_profiles_email;

ALTER TABLE profiles
ADD CONSTRAINT uq_profiles_email UNIQUE (email);
```

**Rationale**: Instead of relying on FK to `auth.users`, we now guarantee email uniqueness. Email is the actual identifier for user lookups and authentication.

#### Step 3: Add Index on Email
```sql
CREATE INDEX IF NOT EXISTS idx_profiles_email
ON profiles(email);
```

**Rationale**: Supports fast lookups by email for authentication and user queries.

### Backend Code Changes

**File**: `backend/internal/api/handlers/admin.go`

## Architecture Decisions

### Why Remove FK Instead of Creating Auth User?

**Considered Alternatives**:

1. ❌ **Call Supabase Auth API to create user on approval**
   - Would require additional API credentials and complexity
   - Supabase Auth is designed for frontend signup, not backend creation
   - Adds external dependency during approval process

2. ❌ **Use database trigger to create auth user**
   - Triggers can't call external Supabase Auth API
   - Would require custom stored procedure complexity
   - Harder to debug and maintain

3. ✅ **Remove FK constraint and use email-based lookups** (CHOSEN)
   - Simple: Addresses root cause directly
   - Maintainable: No hidden triggers or external calls
   - Performant: Email index provides fast lookups
   - Aligns with workflow: `pending_user.id` → `profiles.id` directly

### New Architecture

```
User Registration Flow
│
├─ Frontend: User fills registration form
│
├─ Backend: POST /auth/register
│  ├─ Validate credentials
│  ├─ Hash password
│  ├─ Generate UUID for pending_users
│  └─ INSERT INTO pending_users (id=uuid, email, name, password_hash, metadata)
│
├─ Wait for Admin Approval
│
├─ Admin: POST /admin/approve-user
│  ├─ Validate admin role (RBAC)
│  ├─ Fetch pending user from pending_users
│  ├─ INSERT INTO profiles (id=pending_user.id, email, name, etc.)
│  │  └─ No FK violation! (constraint removed)
│  ├─ UPDATE pending_users SET status='approved', approved_by=admin_id
│  └─ User can now login with email + password
│
└─ Authentication: User can login
   ├─ Frontend: POST /auth/login (email, password)
   ├─ Backend: Validate email in profiles
   ├─ Backend: Verify password hash (from pending_users or profiles)
   └─ Backend: Issue JWT tokens
```

### Data Integrity

**Unique Constraints Now**:
- `profiles(email)` - UNIQUE, ensures no duplicate active users
- `pending_users(email)` - Implicit unique during registration
- `pending_users.approved_by` - FK to profiles(id) ✅ (already correct)
- `pending_users.rejected_by` - FK to profiles(id) ✅ (already correct)

**Identity Chain**:
```
pending_user.id (app UUID) ──approval──> profiles.id (same UUID)
                ↓                              ↓
         unique by email                unique by email
         (indexed)                        (indexed)
```
