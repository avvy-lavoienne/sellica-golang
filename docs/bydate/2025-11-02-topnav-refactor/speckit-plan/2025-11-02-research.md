# Research Phase: TopNav Component Auth System Integration

**Date**: 2025-11-02  
**Feature**: TopNav Component Refactoring and Modularization  
**Phase**: Phase 0 - Research & Clarification Resolution

## Executive Summary

This research phase analyzes the multi-app authentication architecture (SELLICA, SILPANA, SELLY AI) and the critical auth system flow through the Go backend. The TopNav component refactoring must properly integrate with three distinct authentication patterns while maintaining security, performance, and user state consistency across applications.

### Key Authentication Flows

#### Flow 1: User Login (SELLICA/SILPANA/SELLY AI)

```
1. User clicks Login on frontend
2. Frontend: GoAuthAPI.login(email, password)
3. Go Backend receives POST /auth/login
4. Go Backend validates credentials against Supabase auth.users
5. Go Backend issues JWT token (sub=user_id, email, role, exp)
6. Go Backend stores JWT in token cache (15 min TTL)
7. Frontend receives token, stores in localStorage
8. Frontend: GoAuthAPI.getProfile() to fetch avatar
9. Go Backend: SELECT * FROM profiles WHERE id=$1
10. Frontend receives user object with avatar_url
11. layout.tsx sets user context for entire app
12. TopNav receives user via props and displays menu
```

#### Flow 2: TopNav User Menu Rendering

```
1. TopNav.tsx receives user: User | null from layout.tsx
2. UserMenuDropdown.tsx tries to render avatar
3. If avatar_url missing → calls GoAuthAPI.getProfile()
4. Go Backend validates JWT in Authorization header
5. Go Backend checks token in cache (fast path)
6. If not cached → validates JWT signature with Supabase JWT secret
7. Go Backend fetches profile from Supabase
8. Frontend receives avatar_url, updates user state
9. UserMenuDropdown renders fallback initials while loading
```

#### Flow 3: Search Query (Admin Only)

```
1. User types in SearchBar
2. SearchBar debounces 300ms
3. If user.role !== "admin" → skip ticket search
4. SearchBar calls Supabase directly (frontend)
5. Frontend: supabase.from("silpana").select(...)
6. Supabase RLS checks: user is admin?
7. Supabase returns matching tickets or denies access
8. SearchBar displays results or error
```

#### Flow 4: Notifications Real-time Update

```
1. NotificationsDropdown mounts
2. Subscribes to Supabase real-time: notifications channel
3. Fetches initial notifications via GoAuthAPI or Supabase RLS
4. When notification read/unread status changes:
   - Row updated in public.notifications table
   - Supabase broadcasts to subscription channel
   - Frontend receives real-time update
   - NotificationsDropdown UI updates (no page reload)
```

#### Flow 5: Logout

```
1. User clicks Logout in UserMenuDropdown
2. UserMenuDropdown calls GoAuthAPI.logout()
3. Go Backend receives POST /auth/logout
4. Go Backend removes JWT from token cache
5. Go Backend updates session status in Supabase (if SILPANA)
6. Frontend clears localStorage (auth token + user info)
7. Frontend unsubscribes from all Supabase subscriptions
8. Frontend navigates to login page
```

## Three Apps Authentication Pattern

### SELLICA (Main Civil Records App)

- **Auth Source**: Supabase JWT (Go backend validates)
- **User Roles**: user, admin, moderator
- **Session Type**: Stateless JWT (token in localStorage)
- **Permissions**: Data-Rekam read/write, exports, reporting
- **TopNav Features**: Full search (admin only), notifications, profile
- **Routing**: Protected routes require authentication (layout.tsx enforces)

### SILPANA (Ticketing System)

- **Auth Source**: Supabase JWT + Session table
- **User Roles**: user, admin, anonymous (for submissions)
- **Session Type**: Dual-mode: JWT + database session for tracking
- **Permissions**: Ticket CRUD, analytics (admin), status updates
- **TopNav Features**: Ticket search (admin only), ticket notifications
- **Anonymous Access**: Direct Supabase INSERT with RLS permission
- **Key Difference**: Tracks sessions in database for audit purposes

### SELLY AI (Chat System)

- **Auth Source**: Supabase JWT (Go backend validates)
- **User Roles**: user (chat access only)
- **Session Type**: Stateless JWT
- **Permissions**: RAG queries, conversation history
- **TopNav Features**: User menu (minimal), theme toggle, limited search
- **Special Handling**: Chat context persists across page reloads

## Key Decisions

### Decision 1: JWT Token Storage Location

**Decision**: localStorage (current approach maintained)

**Rationale**:
- SPA architecture requires client-side access to token
- Supabase auth.users table trusts Go backend validation
- HttpOnly cookies not feasible (frontend needs token for API calls)
- Risk mitigated by:
  - HTTPS only in production
  - 15-minute token TTL
  - Automatic logout on tab close (clear localStorage)
  - Audit logging of all auth events

**Alternatives Considered**:
- HttpOnly cookies: Would require server-side session (architecture change)
- sessionStorage: Same risk as localStorage, worse UX
- Memory only: Lost on page reload (unacceptable for user experience)

### Decision 2: Auth Validation Point

**Decision**: All protected endpoints validate JWT through Go backend middleware

**Rationale**:
- Single source of truth for auth decisions
- Audit logging in one place
- Token cache provides <5ms validation
- Constitution Principle I (SOA) requires centralized auth service

**Flow**:
```
1. Frontend sends request with Authorization: Bearer {token}
2. Go backend middleware extracts token
3. Check token cache (15 min TTL)
4. If miss, validate JWT signature with Supabase JWT secret
5. Extract UserClaims (sub, email, role, permissions)
6. Store in request context for handlers
7. If validation fails → 401 Unauthorized
8. If user not admin but admin required → 403 Forbidden
```

### Decision 3: Real-time Notification Subscription

**Decision**: Supabase real-time with frontend subscription (not Go backend)

**Rationale**:
- Supabase built-in real-time is optimized for this
- Reduces Go backend load
- Automatic reconnection handled by Supabase client
- RLS policies enforce user can only see own notifications

**Trade-off**:
- Frontend complexity: Must manage subscription lifecycle
- Mitigation: NotificationsDropdown handles subscribe/unsubscribe

### Decision 4: Avatar Fetch Timing

**Decision**: Lazy fetch on TopNav mount (not in layout.tsx auth flow)

**Rationale**:
- layout.tsx auth flow must complete fast for page render
- Avatar is non-critical (fallback to initials works)
- GoAuthAPI.getProfile() called by UserMenuDropdown
- Cache layer keeps subsequent calls <5ms

**Flow**:
```
1. layout.tsx: Quick auth check, set minimal user object (id, email, role)
2. TopNav mounts, UserMenuDropdown mounts
3. UserMenuDropdown effect: If !user.avatar_url, call GoAuthAPI.getProfile()
4. Go backend: Validate token → fetch from Supabase profiles
5. Frontend: Update user with avatar_url → re-render
6. User sees initials immediately, avatar appears when ready
```

### Decision 5: Logout Cleanup

**Decision**: Multi-step cleanup to ensure complete session termination

**Rationale**:
- Security: Token must be invalidated immediately
- User experience: Clear feedback
- Subscription cleanup: Prevent orphaned listeners

**Cleanup Sequence**:
```
1. UserMenuDropdown: Disable logout button (show spinner)
2. Frontend: Clear localStorage (auth_token, user_info)
3. Frontend: Unsubscribe from all Supabase subscriptions
4. Backend: POST /auth/logout (validate token, remove from cache)
5. Backend: Update session status in silpana.sessions (if SILPANA user)
6. Backend: Log auth event for audit trail
7. Frontend: Redirect to login page (useRouter.push("/login"))
8. If logout fails: Show toast error, allow retry
```

## Dependencies on Go Backend

### Required Endpoints

1. **POST /auth/login**
   - Input: email, password
   - Output: JWT token, user object (id, email, name, role, avatar_url)
   - Used by: layout.tsx auth flow

2. **GET /auth/profile**
   - Input: Authorization header with JWT
   - Output: User profile with avatar_url
   - Used by: UserMenuDropdown lazy fetch

3. **POST /auth/logout**
   - Input: Authorization header with JWT
   - Output: Success/error status
   - Used by: UserMenuDropdown logout handler

4. **GET /auth/verify**
   - Input: Authorization header with JWT
   - Output: Valid token response or 401
   - Used by: Optional token refresh checks

### Middleware Requirements

1. **OptionalAuthMiddleware**
   - Validates JWT if present, doesn't fail if missing
   - Sets `ctx.User` if token valid
   - Used by: Public endpoints (search shortcuts, theme toggle)

2. **RequiredAuthMiddleware**
   - Returns 401 if no valid JWT
   - Extracts user claims to context
   - Used by: Protected endpoints (profile fetch, notifications)

3. **AdminRoleMiddleware**
   - Returns 403 if user.role !== "admin"
   - Used by: Admin-only endpoints (admin search, data exports)

## Supabase RLS Policy Integration

### Policies for TopNav Features

**notifications table**:
```sql
-- Users see only their notifications
CREATE POLICY "users_see_own_notifications" ON notifications
FOR SELECT USING (auth.uid() = user_id OR auth.jwt() ->> 'role' = 'admin');

-- Users mark their notifications as read
CREATE POLICY "users_update_own_read_status" ON notifications
FOR UPDATE USING (auth.uid() = user_id OR auth.jwt() ->> 'role' = 'admin')
WITH CHECK (auth.uid() = user_id OR auth.jwt() ->> 'role' = 'admin');
```

**silpana table** (for ticket search):
```sql
-- Admins see all tickets, users see only their own
CREATE POLICY "silpana_select_by_role" ON silpana
FOR SELECT USING (
  auth.jwt() ->> 'role' = 'admin' 
  OR auth.uid() = user_id 
  OR user_id IS NULL  -- anonymous submissions
);
```

**profiles table** (for avatar/user info):
```sql
-- Users see own profile, admins see all
CREATE POLICY "profiles_select_own_or_admin" ON profiles
FOR SELECT USING (
  auth.uid() = id 
  OR auth.jwt() ->> 'role' = 'admin'
);

-- Users update own profile
CREATE POLICY "profiles_update_own" ON profiles
FOR UPDATE USING (auth.uid() = id)
WITH CHECK (auth.uid() = id);
```
